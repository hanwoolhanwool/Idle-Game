# 기술 명세서(문서) 작성 규칙

이 프로젝트에서 **코드 기술 명세서를 작성·갱신할 때** 따르는 규칙이다.
코드 작성 규칙(OOP·SOLID·품질 기준)은 [CLAUDE.md](../../CLAUDE.md)에 있고, 이 문서는 그중 **문서화 규약만** 분리해 담는다.

## 0. 대원칙

- 명세서는 **"어떻게(How)"** 를 다룬다. 게임 재미·밸런싱 의도 등 "무엇을·왜"는 기획서(GDD)에 두고 **링크만** 건다.
- **살아있는 문서(living document)** 로 취급한다. 완벽함보다 코드와의 정합성이 우선 — 코드가 바뀌면 같은 PR에서 문서를 갱신한다.
- 표·다이어그램을 글보다 우선한다. 시각화는 GitHub 렌더링 **Mermaid**(Diagram as Code)로만 하고, 그림 파일을 그리지 않는다.
- 응답·문서 서술은 한국어, 설계 근거를 함께 제시하는 톤을 따른다.

## 1. 문서 종류 (머리말에 반드시 선언)

| 종류 | 언제 | 특징 |
|------|------|------|
| **설계 명세 (TDD)** | 구현 전·중 | Scope·인터페이스 선확정·TBD·테스트 케이스가 필수 |
| **아키텍처 명세 (as-built)** | 구현 후·포폴 | 실제 코드와 일치, SOLID 근거·확장 여지 강조 |

각 문서 최상단에 머리말을 둔다:

> **종류**: 설계 명세 / 아키텍처 명세 · **상태**: Draft / 구현중 / 완료
> **최종 갱신**: YYYY-MM-DD · **관련 기획서**: (링크, 없으면 `해당 없음`)

## 2. 저장 위치·구성

- 모든 문서는 `docs/` 아래에 둔다. 최상위 분류: `specs/`(아키텍처 명세) · `design/`(설계·계획) · `reports/`(분석·기록) · `conventions/`(규약).
- `docs/README.md` = **문서 허브**: 전체 아키텍처 개요 + **도메인 폴더 인덱스**. 상위 허브는 개별 문서가 아니라 **도메인 폴더**를 가리킨다. (+ 심사자용 "대표 명세 추천 순서" 큐레이션)
- 기능별 명세서는 **도메인 폴더**로 나눈다: `docs/specs/<도메인>/<기능>.md`. 도메인은 코드의 `Features/<도메인>` 구조를 **미러링**한다. (예: `docs/specs/player/state-machine.md`, `docs/specs/enemy/target-provider.md`)
- 파일명은 **서술형 kebab-case**. **전역 번호 접두사는 쓰지 않는다**(폴더 이동 시 재번호 방지). 읽는 순서가 중요한 폴더 안에서만 국소 번호(`01-`, `02-`)를 선택적으로 붙인다.
- 한 도메인 폴더에 문서가 **3개 이상이면 그 폴더에 `README.md` 인덱스**를 둔다.

## 3. 공통 섹션 (● 필수 / ○ 문서 종류에 따라 선택)

1. ● 개요·목적 — 2~3줄 + 기획서 링크
2. ● **범위(Scope)** — 포함 / **미포함(Out of scope)**. 미포함 명시가 스코프 분쟁 방지에 가장 중요
3. ● 요구사항·설계 목표 — 표(요구사항 → 설계적 해석)
4. ● 시스템 구조 — 구성요소 표 + Mermaid `classDiagram`
5. ● 데이터 구조 — ScriptableObject 설계, 기획자가 코드 없이 조정할 값 명시
6. ● 상세 로직·상태 — `sequenceDiagram`/`stateDiagram-v2`/`flowchart` + 엣지 케이스
7. ● 인터페이스·의존성(경계) — 다른 시스템과의 계약·API. **구현보다 먼저 확정**
8. ● 설계 포인트 — SOLID 매핑 표 + 하이라이트 패턴
9. ○ **Unity 특화** — 생명주기·초기화 순서·풀링 / 씬·프리팹 구조 / **성능 예산(GC Alloc·프레임당 연산)** / 에디터 툴 필요 여부
10. ○ 테스트 케이스 — 검증 방법·확인 항목 (설계 명세는 필수)
11. ○ **리스크·미결정(TBD)** — 성능 우려·미정 사항을 숨기지 말고 명시
12. ● 확장 여지 — "지금 만들지 않되 막지 않을 것"
13. ● 파일 위치 — `구분 | 파일 | 경로` 3열 표. 단, 파일이 소수(2~3개)면 `파일 | 경로` 평면 표를 허용한다

## 4. 작성 원칙

- 아키텍처 명세는 반드시 **실제 코드를 읽고** 작성한다. 클래스·메서드·필드명을 소스와 일치시킨다(추측 금지).
- 설계 명세는 **메서드 시그니처·책임 수준까지만** 쓴다. 구현 세부는 코드에 맡긴다.
- **인터페이스(경계)부터 못박으면** 병렬 작업이 가능해진다 — 7번을 먼저 채운다.

## 5. Mermaid 문법 주의 (GitHub 렌더 안정성)

- `classDiagram` 제네릭에 콤마를 쓰지 않는다. `Dictionary~K,V~`(깨짐) → `-name : Dictionary` 형태로 표기.
- 스테레오타입(`<<...>>`)에 특수문자(가운뎃점 `·` 등)를 넣지 않는다. 예: `<<readonly struct>>`.
- `flowchart` 노드 레이블에 괄호·콜론이 들어가면 `"..."`로 감싼다.

## 6. 커밋

- 문서만 따로 스테이징한다(코드 변경과 섞지 않는다). 타입 `docs`, 제목·본문은 한국어. (컨벤션: [git-commit-convention.md](./git-commit-convention.md))
- 코드와 문서가 어긋나면 **같은 PR에서** 갱신한다.
